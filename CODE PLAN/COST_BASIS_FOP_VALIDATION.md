### P1 中的决定

- 旧页面在 P1 不自动把 FUT 账本转到 FOP 页面。在 FOP 页面能导出或删除之前，旧 FUT 账本的查看、导出、删除仍只在旧页面可用；FOP 页面给出链接。
- FOP 页面用公共层的请求客户端；旧页面保留自己的 `request()`，本阶段不迁移，以免改动面过大。
- 契约读取器目前只在测试中使用。P2 的服务端域校验必须接受全部正例、拒绝全部反例。
- DDL 草案中：
  - `settlement_type` 只允许 `physical_future`，`option_strike` 必须大于 0，对应 §1.2 的首版边界；
  - `product_rules` 不设 CHECK，由代码中的支持清单校验，这样新增产品不必重建表；
  - 周期表沿用计划名 `cost_basis_fop_cycles`，只存边界；
  - 没有 ROLL 表，也没有资金对账表。

  - as-of 视图：时间已结束的事件已发生；顺序证据排在某个已发生事件之前的事件也已发生（券商序号证明它更早）；其余只开始未结束的事件使相关合约数量和它可能改变的汇总项为空，且只影响它所属的周期（迟到费用是源成交的周期）；周期和它的边界按整本账本确定，边界所在组全部发生之后才算已过；

  - 中间步骤不舍入。
- **服务端时间线（`cost_basis_fop_domain.py`）**：

### P3 中的决定

- 核心直接回放导出的账本图，不另定输入格式；P5 页面通过导出动作取得同一份数据。
- 稳定来源键依次为：主来源（命名空间:引用），种类，数量，价格，现金，费用，事件 ID。事件 ID 只在其余全部相同时决胜，这时顺序不影响任何数字。
- 顺序证据的格式定为 `范围#序号`，其他写法视为没有证据。这只会在顺序确实有影响时导致拒绝，不会放过歧义。
- 原因码：`no_quote`、`invalid_quote`、`missing_mark:<合约>`、`order_ambiguous:<事件>`、`overdraw:<事件>`、`delivery_time_unresolved:<事件>`、`event_time_unresolved:<事件>`、`cycle_unattributed:<事件>`、`unknown_opening_cost:<合约>`、`opening_premium_unknown:<合约>`、`baseline_not_at_reference:<合约>`、`not_applicable_full_history`、`as_of_before_baseline`、`history_before_baseline`、`no_future_position`、`multiple_future_contracts`、`binding_conflict:<合约>`。回本价同时有多个原因时，数据缺口优先于基线范围，基线范围优先于持仓形态。
- `gaps` 列出期初价值、所列合约的数量和剩余净权利金、各合约实现损益、全部汇总项和卖方口径中为空的项；行内的报价类数字不重复列出，原因已在该行。
- 以参考价入账的基线期权，其剩余净权利金记为未知：`O_B` 是价值抵扣，不是收到的权利金（§9.2）。
- ROLL 推导首版只处理 FUT 成交；期权的换月同样是两条真实成交，经济结果不受影响，展示分组留到页面阶段需要时再加。

### P4 中的决定

- **没有真实样本，全部经济行保持 `synthetic_only`。** 写入报表行的测试用 `verified_capabilities()` 代替真实验收；真实用户目前只能预览，或逐行手工认领。
- **同秒顺序**（审查修正 2 改定）：报表的行序不是成交顺序的证据，同秒各行不带顺序证据；顺序影响结果时由核心判为歧义并阻断。最初按行在该秒内的位置编号的做法已撤销。
- **成交明细优先于委托汇总**：Activity 同时有 Order 与 Trade 行时导入执行明细，委托必须等于其明细之和（数量、均价、佣金），否则阻断。
- **跨格式的同一成交在预览中剔除**（审查修正 1、3、7 改定）：不同引用是否同一成交只有内容能证明，服务端无从判断，所以匹配在导入器完成。一对一匹配后还要求费用、现金、开平、交易所交易日和期权绑定一致，否则阻断；委托与其执行明细只凭双方都写明的同一券商委托编号认定；无法证明相同、也无法证明不同的同日成交阻断。全部行都已按其他引用存在、或期间没有成交时，仍发送只登记期间的请求（不带包）。
- **TWS 成交被报表那一行替代**，在同一事务内作废，佣金以报表为准；报表期间内有 TWS 成交而报表没有，阻断（F20）。
- **时区**：用户声明优先；否则取报表 WhenGenerated 的缩写，只接受能唯一对应一个时区的（CST 不接受）。夏令时重复的本地时刻记为两种读法之间的时间范围，不存在的时刻阻断。只有交易日的 Flex 行覆盖交易所时区中前一日 00:00 至当日 24:00。
- **基线**：B 为报表期间首日的本地零点。FUT 期初需要成交成本（整期未动时取未平仓段落的成本价）或用户给出的价格，否则阻断；FOP 缺成本时记为数量存根（`unknown_cost`）。
- **报表绑定凭据**：服务端自己读证据行，要求写明期权、写明其标的期货，并由交割月字段或与交割月一致的本地代码显示该期货的交割月。
- **费用调整类行不导入**：没有样本无法确认其版式和与成交的关联；迟到费用仍由手工或 TWS 录入，测试覆盖其与导入的配合。
- **用 v12 而不是改写 v11**：P2 已在本地 main，后端重启就会生成 v11 文件，不能原地改表。本机真实账本当时仍是 v10（只读查询），live 后端未重启。

### 守卫本身的有效性

### P5 中的决定

- **估值留在页面，服务端只报证据。** 这样 §10.3 的降级、方向、新鲜度都在一处纯函数里，可以用可控时钟测试；服务端不替页面“挑一个价”。
- **IB 快照的收盘价没有日期。** IB 的 close tick 不说是哪一天，所以来自 IB 的收盘价不能成为“带日期的参考”，IB 实际只能提供中间价和单边价两级；合成后端和测试覆盖结算/收盘参考一级。给 IB 结算价补日期（例如读前一日日线）留到以后。
- **页面时钟只用来给报价计龄，不给报价盖日期。** 报价时刻是服务端收到行情的时刻（`ticker.time`）；测试和浏览器脚本通过 `setClock` 控制页面时钟来验证 120 秒新鲜度。
- **P5 不开放写入。** 两台服务器的 `fop_writes_enabled` 仍然关闭，页面据此停用写按钮；只有合成后端和测试开启写入。
- **报表覆盖记录随恢复存档。** 从备份恢复会把原报表覆盖记录与原历史一起存档（P2 的行为），恢复后覆盖显示“未核对”，需要时重新导入报表登记期间；页面恢复成功后会说明这一点。

### 第 2 步：固定种子随机回归

首次运行发现两个真实问题，都先用测试复现再修正：

1. **后一份 Flex 报表绑不上账本里已有的期货。** Flex 期权行只用 `UnderlyingConid` 写标的；导入器只在“本文件新建的合约”里找，所以期货若在前一份报表导入过，期权就成了待补全，同一文件里的指派被 `binding_missing` 阻断。现在也在账本已有的期货里找，但只在本文件确实出现了该期货（它的一行或合约信息）时才算证明，这正是服务端签发凭据时核对的行；本文件没出现就仍是待补全。测试 `DeliveryTests.test_a_later_file_binds_an_option_to_the_stored_future_its_rows_name`。
2. **已存为待补全的绑定，后来的报表证明了也补不上。** 计划 §4.3 允许用报表里明确的标的资料补齐绑定（已到期期权往往查不到券商）。现在导入预览列出“本文件证明的期权绑定”，阻断说明写明“本文件证明了 X，先采纳再预览”；页面提供“采纳报表证明的绑定并重新预览”：服务端自己读这些行并签发凭据，每个绑定一次版本受控的元数据提交（`adopt_binding`，不改经济行），然后按新版本重新预览同一文件。从交割腿推断的对应关系不算证明，只用期权行自己写明的标的。测试见管线 `test_a_later_file_that_proves_a_stored_unresolved_binding_offers_its_adoption` 与页面用例（重复点击只请求一次、被拒不提交、写入关闭不发送）。

生成器自身的两处错误（动作落在合约到期之后；分笔订单与下一个动作同秒）在同一轮修正，都不是被测代码的问题。
