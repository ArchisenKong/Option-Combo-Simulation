## 1. 产品范围与冻结决策

### 1.1 建账与路由

建账第一步必须显式选择类型；新建表单不预选，以免输入 CL 后误建股票账本。

| 用户看到的类型 | 持久化兼容值 | 进入页面 | 允许的基础资产 |
| --- | --- | --- | --- |
| ETF / LETF / 股票 | `secType=STK` | `cost_basis.html` | STK + OPT，保留当前功能 |
| 期货 / 期货期权（FOP） | `secType=FUT` | `cost_basis_fop.html`（新增） | 指定产品范围的 FUT + FOP |

- `secType` 仍表示账本底层资产类型，不能把已有 `FUT` 改成券商期权类型 `FOP`。页面可派生 `bookKind=equity/fop`，不再保存第二个可能矛盾的类型字段。
- 账户、根代码、类型、币种共同确定活动账本，保持现有唯一约束。同账户的 CL 与 MCL 分属不同根代码，不自动合并。
- 类型创建后不可原地切换。录错类型时使用正确类型的新账本和其导入流程，不转换历史事件。
- 原 COST_BASIS 入口、账户选择与账本列表继续可用。选择账本时根据后端返回的真实类型跳转，链接携带 `bookId`；不能仅凭 URL 指定计算引擎。
- 打开错误页面、过期书签或另一账户的缓存选择时，先读取账本元数据，再正确路由；加载期间不渲染旧账本结果、不发送旧账本写请求。
- FOP 页面与 ETF 页面互相切换时清理请求代际、报价、草稿及本地情景；用户设置按 `bookId + engineVersion` 隔离。
- 服务端建账同样不设默认类型。`create_cost_basis_book` 目前在缺省时按 `STK`、每张 100 建账，须改为要求显式 `secType`；FUT 账本的点值来自已核实的合约条款或显式输入，不使用 100 之类的默认值。
- 每个 FOP 账本的引擎/语义版本保存在服务端的 FOP 账本元数据中（§8.1），每次写入都由服务端核对；没有该元数据的 FUT 账本不能写入。

### 1.2 首版交付边界

首版完整支持 **USD、NYMEX 标准 CL FUT，以及已证明交割到一张 CL FUT 的标准月度/周度 FOP**，包括多空、买方期权、纯期权阶段、提前平仓、提前指派/行权、部分换月和跨月多空。

产品资格由具体合约条款确认。`symbol=CL` 或 `secType=FOP` 本身不足以证明支持；`product_registry.js` 的默认 `tradingClass` 也不是所有 CL 期权的统一交易类。

首版不扩展到现金结算期权、期货式逐日结算权利金产品、价差期权、非标准交割包、跨产品换月、外币折算、零或负 strike 的 FOP，或实物原油收发货账。识别到这些记录时明确说明不支持，不能按普通 CL 交割强行入账。零/负 FUT 价格仍在首版范围内（§6.4）。

目前两台机器上都没有 FUT 账本，不存在需要兼容的旧 FUT/FOP 数据（§8.2）。CL 以外的产品在补齐乘数、交割、现金结算方式、时钟和真实报表验收前不能建账；新增产品按同一门槛进入支持清单。

### 1.3 延续范围

- 默认同一账户、同一根代码的全部有效 FUT/FOP 事件进入该账本的连续总账，期货换月不另建账本。
- 增加可选“记账周期”：默认一个连续周期；仓位暂时归零不自动结束，后续建仓默认仍承接该周期历史。
- 用户仅能在全部 FUT/FOP 余额为零、没有未解决交割/数量问题的边界结束周期并开始新周期。旧收益留在整本累计中，不抵扣新周期回本价。
- 迟到的费用可按原成交证据归属已关闭周期并重算其结果；迟到的仓位事件必须重新证明该周期在关闭边界确实归零。不能为了继续导入而静默移动周期边界。
- 周期只保存边界，不在事件上保存周期归属。边界锚定在使全部 FUT/FOP 余额归零的那条事件上；持仓事件按经济顺序推导周期，迟到费用通过源成交或费用所属期间推导（§13.2）。任何写入（含补录、冲销、重建）之后，所有已关闭边界仍须满足归零条件，否则整批拒绝；冲销锚点事件必须在同一次提交中撤销或重新指定该边界。
- 首版不支持同一时间把相同 CL 持仓分配给多个并行子策略。需要这种归属时必须另立数量分摊设计，不能用 `includeInCost=false` 隐藏账户持仓后声称已全账户对账。
- FOP 账本中带持仓数量的事件（FUT 成交、FOP 成交、行权/指派、到期）不允许 `includeInCost=false`：首版没有子策略分摊，排除这类事件只会让逐合约数量与券商持仓脱节。只有不带数量的独立现金事件（如与本策略无关的费用）可以排除，并在对账范围中显示。

### 1.4 CSV 是主输入，手工是例外处理

目标流程为：选择 IBKR Activity Statement / Flex CSV → 自动提取全部相关 FUT/FOP 成交、费用、交割及来源 → 自动去重和重放 → 展示结果与缺口 → 一次确认后原子入账。证据充分的正常记录不需要逐笔手工录入、手工计算盈亏或人为指定开平仓配对。

长期历史以用户导入的报表为主，不依赖 TWS 近期成交窗口，也不只读取当前未平仓合约。这里的“自动获取”指从提供的 CSV 自动解析；自动登录券商下载或定期拉取 Flex 报告另属采集功能，不作为本次已经包含的能力。

支持完整年度文件以及按月、按年连续追加；跨年不重置已实现损益。完整历史中的所有已平期货月份必须保留，即使它们不再出现在期末持仓表。若用户未主动结束记账周期，历次盈利和亏损都延续到当前周期。

### 1.5 首版一览

首版（P0–P6）交付：

- 独立 FOP 页面；建账时显式选择类型，按后端返回的真实类型路由。
- 仅 USD、NYMEX 标准 CL FUT，以及已证明交割到一张 CL FUT 的月度/周度 FOP。
- 真实交割月、最后交易日、期权到期分开保存，逐合约回放。
- 以 IBKR CSV 为主输入的连续多年历史；换月只写两条真实成交，ROLL 分组在读取时推导。CSV 行类型按能力清单逐类开放写入（§9.7）。
- 完整经济盈亏、只持一个 FUT 合约时的卖方等效回本价、逐合约一次性报价。
- 可审计的交割预览；只读券商边界。

首版不含：P7 压力曲线、持久化的 ROLL 关联、子策略分摊、零/负 strike、CL 以外的产品、旧 FUT 数据迁移、自动拉取报表、日结/资金对账（§6.3）。

## 2. 当前代码现状与必须补齐的缺口

以下为代码核对结论，不把旧计划中的完成说明当作新版本验收。

| 位置 | 目前已有 | 本计划要求 |
| --- | --- | --- |
| `cost_basis.html` / `js/cost_basis.js` | 已有 STK/FUT 选择，同一页面大量条件切换 | 建账类型显式化；FOP 独立页面和控制器 |
| `js/cost_basis_core.js` | FUT 分月回放、实现损益、FOP 交割、ROLL 与综合成本 | 独立 FOP 核心；逐合约估值、完整盈亏、成本可用状态 |

| `js/cost_basis_import.js` | FUT/FOP 导入、交割配对、合成换月、来源两腿 | 普通 FOP 成交也要保存对应 FUT；新换月只写两条原始成交，ROLL 分组读时推导 |
| `cost_basis_executions.py` / 前端成交导入 | 普通成交支持四种证券类型；部分价格检查统一拒绝负数 | FUT 允许零/负成交价；FOP 行权价与期权报价分开验证 |
| TWS AvgCost 序列化 | 存在 `abs(averageCost)` 和正数门槛 | FUT 基准价保留符号及单位证据，不直接照搬 STK 规则 |
| `js/cost_basis.js::_absorbAvgCost` | FUT 路径可用不同月份中的某一市价覆盖单一 `marketPrice` | 删除 FOP 的单一根代码市价真相，使用合约报价映射 |
| 主页面合约解析 | `underlyingFutureId`、`underConId`、真实 `contractMonth` 验证 | 复用经验证的纯逻辑/服务，不加载交易壳，不复制浏览器选择为证据 |
| COST_BASIS 行情/压力端点 | 当前限定 STK；压力测试为股票资产估值模型 | FOP 新的有界只读报价路径；股票压力测试不作为 FOP 计算器 |
| 测试 | 已有 FUT/FOP 固定回归和独立随机账本模型 | 加真实 CL、月份错位、负价格、部分换月、备份完整性等专项 |

尤其注意：CL 期货在交割月之前的月份停止交易。[CME 200 章](https://www.cmegroup.com/rulebook/NYMEX/2/200.pdf)与 `ib_server.py::_remember_verified_underlying_contract_month` 均说明了这一区别。不能照搬现有“YYYYMM 与 YYYYMMDD 截取后视为同月”的假设。

**现存缺陷（2026-09-24 用现有核心复现）。** 月份截取不只是新引擎要补的缺口，也会让现有 FUT 账本静默算错：

- CSV 导入按 `expiry` 读取合约日期，其列名别名包含 `lasttradedate`；TWS 成交带回 `lastTradeDateOrContractMonth`。对 CL 来说，两者都是最后交易日。
- 手工表单用 `type="month"` 输入，存的是真实交割月。
- `js/cost_basis_core.js::futureKey`、`cost_basis_store.py::future_key` 以及 TWS 基线的同键查询都只取前六位。

合成场景：手工录入 CLZ6 +1 @70（`2026-12`，无 conId），CSV 录入 CLF7 −1 @71（`20261218`），CSV 录入 CLZ6 +1 @69（`20261119`）。

- 现有核心的结果：把 CLF7 空单当作平掉 CLZ6 多单，得出 +1000 已实现盈利、剩 1 张 @69、综合成本 68，且没有任何警告。
- 真实情况：CLZ6 +2、CLF7 −1 的跨月价差，已实现为 0。
- 为什么没有警告：身份冲突检查只在 conId 多于一个时报警，而手工那一行没有 conId。

两台机器上都没有 FUT 账本，这个缺陷尚未影响真实数据。P0 先关闭现有页面的 FUT 建账与写入（§13），不在旧引擎上修补。

## 3. 不变量

1. **账本是事实来源。** TWS 持仓快照只检测差异；真实成交和经明确确认的临时基线才可入账。期权消失、期货增加不能自动生成交割。
2. **合约身份优先。** 每张 FOP 的真实标的 FUT 固定；换月不修改未平期权的绑定。不同账户、交割月、合约、点值不能静默净额合并。
3. **数量、现金、经济盈亏分开。** FUT 名义本金不进现金；日结现金和成交回放盈亏不得重复计算。
4. **期权权利金只记一次。** 开仓收付已入账；平仓记录实际回款/支出；交割事件的现金只有适用费用。
5. **没有报价不等于价值为零。** 缺少一个必要合约价格时，完整当前盈亏不可用；已知持仓和已实现结果仍可查看。
6. **综合成本不驱动盈亏。** 先由完整事件/持仓算盈亏，再独立计算符合条件的回本价。多月份持仓不套一个“CL 当前价”。
7. **不完整历史不输出完整历史结论。** 数量完整、期初成本完整、绑定完整、当前行情完整、报表覆盖完整分别判断。
8. **计算确定、修改可审计。** 离线重放不查网络、不取浏览器当前时间；修订、绑定补充和周期边界都有版本与来源；ROLL 分组由真实成交确定地推导，不单独持久化。
9. **ETF/LETF 回归隔离。** 不改变股票指派本金、税务成本、拆股、股息、现有保护期权口径和压力测试语义。
10. **独立只读券商边界。** FOP 页面不能发订单、自动 ROLL、行权请求或持续行情订阅；不加载交易脚本。

## 4. 合约、月份与绑定模型

### 4.1 三个不同的时间字段

必须分别保存：

- `optionExpiry` / `optionExpiryAsOf`：期权到期日及可验证的精确截止时刻。
- `futureContractMonth`：期货交割月 `YYYYMM`。
- `futureLastTradeDate` / `futureLastTradeAsOf`：期货最后交易日/时刻。

保留券商原始日期字段及其来源，不用一个 `expiry` 字段同时承载以上三种意义。`lastTradeDateOrContractMonth` 的八位值不能直接截取为交割月，也不能普遍加一个月猜测。

### 4.2 正规化身份

FUT 身份包含 broker/conId、根代码、secType、交易所、币种、真实交割月、localSymbol、点值。FOP 身份再包含 optionRoot、tradingClass、C/P、精确行权价、期权到期、报价乘数、交割类型及对应 FUT 身份。

- 有 conId 时以其定位并核对结构字段；相同 conId 带冲突条款同样拒绝。
- 缺 conId 的历史记录允许使用完整且唯一的结构身份；后续补充券商证据建立可审计对应关系，不能生成虚构 conId。
- 同到期、同 C/P、同 K、同乘数仍可能是不同交易类/不同底层 FUT；不能沿用股票简化键直接归并。
- 同一 root 的零净张数不代表无风险：不同期货合约的多空分别保存。
- 金额乘数 `premiumMultiplier`、FUT 点值 `futurePointValue`、每张期权交割张数 `deliverableFuturesPerOption` 分开。首版 CL 分别为 1000、1000、1，以核实条款为准。

### 4.3 绑定证据与状态

优先使用 IB 合约详情的 `underConId` 解析底层 FUT，再读取该 FUT 的 `ContractDetails.contractMonth`，核对根代码/交易所/币种/点值。主页面已有对应实现；抽取或注入这项服务后供两处使用。

状态固定为 `verified_broker`、`verified_statement`、`manual_attested`、`unresolved`、`conflict`，同时记录来源摘要、观察时刻、条款版本。人工核实不能显示成券商验证。

- 已到期 FOP 可能无法再次通过在线查询补全；允许使用报表中明确的 underlying 资料或有依据的人工核实，不能要求历史重放必须在线。
- 普通历史成交缺绑定但自身身份/数量/现金可唯一确认时，允许保存为待补全记录；只展示已证明的结果，停用交割预览、覆盖判断和完整估值。身份本身歧义或证据冲突则阻断提交。
- 交割入账必须证明实际 FUT 身份及方向。存在已知绑定时必须一致；未知绑定只有报表确实证明对应关系或人工核实后才可补齐。同日同数量的唯一候选不是独立的绑定证明。
- 不把主页面某个 `futuresPool` 当前选项、期权到期月份、连续合约或“当前主力”当作持久证据。
- 合约信息刷新只返回候选证据，不自动改历史。采纳、更正和影响预览通过有版本保护的显式提交完成。

证据采纳还需满足以下可实现约束：

- 浏览器提交 `verified_broker=true` 或状态字符串不构成券商验证。只读解析返回有界、会过期的服务端候选凭据；提交时服务端核对凭据中的 book、合约、证据摘要和版本，再保存证据。断线/过期后重新预览；离线人工输入只能记为 `manual_attested`。报表验证须关联保留的原始字段与来源记录，不能只有一个布尔值。
- 合约条款/绑定版本不可原地改写。仅补充同一合约的 conId/证据时保留稳定的逻辑合约 ID；采纳请求列出受影响事件和原引用版本，事务内记录引用修订的前后值并重放。事件的经济数量/金额不变，账本 digest 必须改变。
- 把已经确认的交割合约改成另一个 FUT 属于经济更正，走有存档的更正/重建流程；不能以“补绑定”为名静默把已实现损益搬到另一月份。旧版本及修订记录随备份保存。

CL 周度期权的对应月份在月度到期边界存在切换规则；月度与周度都具有美式行权特征。依据为 [CME 1011 章](https://www.cmegroup.com/rulebook/NYMEX/10/1011.pdf)与 [CME 310 章](https://www.cmegroup.com/content/dam/cmegroup/rulebook/NYMEX/3/310.pdf)，规则日期由具体合约证据确定，不在前端用粗略日历推定。

## 5. 独立 FOP 计算契约

### 5.1 持仓回放

每个 FUT 单独维护有符号张数 `q_i`、点值 `M_i`、实际/期初基准均价 `A_i` 和带符号基础 `q_i × M_i × A_i`。沿用可解释的加权平均成本：

- 同向增仓加权；部分平仓按该合约当前均价计算毛实现损益。
- `实现损益 = 平仓张数绝对值 × M_i × 原方向 × (平仓价 − A_i)`。
- 反向成交只把超出平仓数量的余量按成交价建立反向新仓；期权 C/O 沿用现有明确反转证明。
- 纯平仓超过可用数量拒绝。FUT 导入有明确 O/C 语义时必须核对；无 O/C 的真实买卖按有符号余额回放，并标明无法推知券商意图。
- 期权逐合约追踪剩余开仓净现金、已结算净收益、多空方向和身份；部分平仓按既定比例分摊，不将全部开仓权利金一次实现。

### 5.2 完整经济盈亏为主指标

对一个历史完整的账本或周期，在时点 t：

```text
Rf       = 由 FUT 成交/交割回放得到的累计毛实现损益
Uf(t)    = Σ [q_i × M_i × (该合约价格 F_i(t) − A_i)]
Co       = 全部 FOP 交易的累计净现金（包括多头、已含这些交易的佣金）
Vo(t)    = Σ [未平期权有符号张数 × 报价乘数 × 该期权价格]
E        = 未包含在 Co 中的期货交易费、交割/到期费及独立净费用
J        = 有证据、明确计入策略的其他经济调整（收入为正）

策略累计经济盈亏 = Rf + Uf(t) + Co + Vo(t) − E + J
```

`Vo` 中多头为正、空头为负。期货不计 `q×M×F` 为已支付资产；`Uf` 只是相对于成交/基线的经济损益，不声称全部尚未现金结算。Co 中的费用不能再次计入 E。

各事件进入哪一项固定如下；同一笔现金只进一项：

| 事件 | 数量影响 | 现金/费用归入 | 卖方降本口径（§5.3） |
| --- | --- | --- | --- |
| FOP 成交（现金含佣金） | FOP 张数 | Co | 空头部分：已平/已结束的进 Rs，未平的计为未平卖方净收入；多头部分不进入 |
| Short FOP 指派 | 关闭 FOP，FUT 按 K | 费用进 E | 费用进 Es；该期权权利金随义务结束进 Rs |
| Long FOP 行权 | 关闭 FOP，FUT 按 K | 费用进 E | 费用不进入；产生的 FUT 进入持仓与 Rf（见 §5.3 路径差异） |
| Short FOP 到期 | 关闭 FOP | 费用进 E | 费用进 Es；权利金进 Rs |
| Long FOP 到期 | 关闭 FOP | 费用进 E | 不进入 |
| FUT 成交 | FUT 张数 | 费用进 E；名义本金不进现金 | 费用进 Es |
| 有明确归属的独立费用/返佣 | 无 | E（返佣为负费用） | 仅归属 FUT 或卖方期权时进 Es |
| 有证据的经济调整 | 无 | J | 仅显式标注归属本口径时进 Js |
| 日结现金、保证金、出入金 | 无 | 不进入；首版不导入这些段落（§6.3） | 不进入 |

同时输出已实现期货毛损益、已结算期权净收益（区分买方/卖方）、未结算期权价值变化、其他费用及调整，分项能加回总额。历史缺失时保留已知分项，总额为不可用或明确的“自基线起变化”，不能把未知值补零。

### 5.3 卖方降本参考价

保持当前产品把 Long Call/Put 独立于卖方降本指标的约定；完整经济盈亏仍包含全部买方期权。

这里排除的是买方期权的权利金及其专属费用；其行权后真实产生的 FUT 仍参与实际期货持仓和 Rf，不能把这部分真实数量隐藏。该参考价不代表包含保护成本的完整策略回本价。

仅当当前周期只持有**一个真实 FUT 合约、非零张数**，必要历史完整且身份无冲突时：

```text
Rs = 已结束义务的卖方 FOP 净收益，包含其开/平仓费用
Es = 纳入降本口径且尚未计入 Rs 的 FUT/交割/独立费用
Js = 明确归属于本口径的其他经济调整

卖方策略等效回本价 = A − (Rf + Rs − Es + Js) / (q × M)
未平卖方期权全部归零假设价
                  = 上式 − 未平卖方期权剩余净收入 / (q × M)
```

q 带符号，空头收益对应提高回补回本水位。未平买方权利金、保证金、出入金和日结现金不能混入。买方交割/到期费用归买方模块，避免通过公共费用桶间接污染卖方成本。

这是对已结算结果的价格换算，**不是含未平期权价值的即时清仓回本价**。界面完整命名并并列显示未平风险；不默认减掉未结算卖方权利金。

| 状态 | 展示规则 |
| --- | --- |
| 单 FUT 合约，历史完整 | 当前实际开仓均价 + 卖方策略等效回本价 |
| 多个 FUT 合约、同向 | 逐合约均价与总美元盈亏；不展示一个可交易的总回本价 |
| 跨月多空或净张数为零但未平仓 | 保留全部合约、显示跨月持仓，不标“已清仓” |
| 没有 FUT、仍有 FOP | 显示期权现金、持仓和经济盈亏；每桶成本不可用 |
| 全部平仓 | 显示周期已实现结果；不除以零、不自动新建周期 |
| 历史/身份不完整 | 显示具体缺口；依赖该缺口的数字不可用 |

暂不分摊共同历史权利金为“每个月份的降本成本”。首版逐月只显示实际均价；若未来增加分摊，必须有显式分配规则且保持总额守恒。

**买方行权的路径差异（接受并标注）。** 买方期权行权时按 K 产生或平掉 FUT，这部分结果进入 Rf，而权利金不进入本口径；如果改为卖出期权兑现同样的内在价值，这笔收入也不进入本口径。因此同一经济结果会因操作方式不同而得到不同的回本价（§5.4“买方行权路径”一行：75 与 80）。

- ETF 账本的 Long Put 行权按 K 卖股，也有同样性质；本计划沿用，不修正。
- 完全消除需要把买方行权产生的 FUT 按行权时的结算价计入本口径，并把 (K−F)×M 归入买方模块。这需要可靠的结算价证据，首版不做。
- 周期内发生过买方行权时，回本价卡片必须提示该数字受行权方式影响。

与现有实现的口径差异如下。新引擎按本计划实现，不照搬旧代码：

| 项目 | 旧 FUT 核心 / ETF 账本 | 本计划 |
| --- | --- | --- |
| 买方期权交割/到期费用 | 旧 FUT 核心计入 `futuresSettlementCash`，进入综合成本；ETF 账本的交割现金同样计入成本口径 | 归买方模块，不进入 Es（有意与 ETF 账本不同） |
| 多个同向 FUT 月份 | 合并成一个综合成本 | 只显示逐合约均价与总盈亏，不给单一回本价 |
| 市价 | 页面级单一 `marketPrice`，多个月份共用 | 逐合约报价映射 |
| 独立费用与 `manual_adjust` | 一起计入 `futuresSettlementCash`，全部进入成本 | 按 §5.2 归属表拆为 E 与 J，只有显式归属的部分进入降本口径 |

## 6. 交割、ROLL、费用和现金的边界

### 6.1 FOP 行权/指派

| 期权原持仓 | 事件 | 每张产生的 FUT 增量 |
| --- | --- | --- |
| Short Put | assignment | +1 |
| Short Call | assignment | -1 |
| Long Call | exercise | +1 |
| Long Put | exercise | -1 |

产生的 FUT 以 K 入账；如果该合约已有反向仓位，正常形成部分/全部平仓或反转。不能强制认定每次交割都是新仓。

交割关闭期权并改变 FUT 数量，在同一事务完成；事件现金只含费用，不记录 K×1000 名义付款，也不再收入权利金。报表 option 行和 delivery FUT 行作为一个复合事件的两份来源证据，只应用一次数量与费用。

不能仅凭同日/同量/同根代码配对；必须核对实际 FUT、方向、交割价、点值、期权绑定及可用的交割标志/来源引用。券商多张汇总成一行时，数量和来源分配必须唯一守恒，否则待人工核实。

提前交割按实际经济时刻重放。到期的 ITM/OTM 推测只能产生内存情景，不能代替券商实录。FOP 交割到 FUT 与 FUT 最终实物交割是不同环节；后者首版不支持，不自动现金结算或自动清仓。

### 6.2 ROLL 的唯一经济来源

**新写入的 ROLL 只写真实 FUT 成交；ROLL 分组在读取时推导，首版不写库。**

- 两端成交各记一次 `futures_trade`。ROLL 分组只说明哪些平旧、开新成交属于同一次换月，不另计损益、现金或手续费，也不保存在数据库中。
- 推导支持一个 ROLL 多次部分成交、两端不同时间完成、只完成一端和数量不等。未配对数量仍是真实持仓，页面显示“换月未完成/另行加减仓”。
- 推导结果给出每笔成交用于本次 ROLL 的数量；累计使用量不得超过该成交的平仓/开仓段，反转成交只可用于相应子段。推导是成交记录的确定函数，同一历史总得到同一分组。
- 有订单/组合/来源证据的配对标为“有证据”；只凭时间相邻的配对标为“候选”。
- 不同根代码、币种、点值、方向不能作为本版普通 ROLL。平旧与开新为不同真实合约且保留持仓方向。
- 加权价差与费用按匹配数量计算，剩余费用/数量归原成交。必须满足每条来源的分配合计等于原数。
- 同数量完整 ROLL 满足 `C_new = C_old + P_new − P_old + fees/(q×M)`；不能再额外扣一次显示出来的 roll spread。
- 期权 ROLL 同样是旧 FOP 平仓 + 新 FOP 开仓，两张期权可绑定不同 FUT；不得视为原期权改到期日。
- 以后如需由用户确认并持久保存的 ROLL 标签，另立设计；标签不得参与经济计算，也不得成为成交冲销的前置条件。

**是否识别为同一组 ROLL，不影响真实成交入账及盈亏计算。** 如果两条普通 FUT 成交本身身份、数量、价格、来源和历史支持完整，但缺少配对证据，应分别正常入账、自动计算平仓盈亏，并把该换月显示为“候选”或“未配对”。不能仅因无法配对 ROLL 而丢弃成交或阻断一份原本经济记录完整的报表；交割身份不明、真实重复疑点等经济问题仍按规则阻断。

不存在需要兼容的旧 `futures_roll` 行（§8.2）。新引擎不写 `futures_roll`；手工换月也只写两条真实成交。

推导顺序固定为：先回放每笔 FUT 成交得到平仓段/开仓段，再按明确组合或来源组证据匹配；组内按 §9.2 的经济顺序分配整数张数，消耗量取两侧剩余量的较小值。多个配对方案都符合证据时，不任意选一组为“有证据”。无证据的候选仅为建议：按用户当前查询区间列出兼容且未被证据组消费的成交段，按经济顺序及稳定来源键排序，不设隐含的同日/同秒窗口。互斥候选不得汇总成“已完成换月”，也不消费真实数量；未匹配历史始终可见。推导算法版本进入导出说明，改变它不得改变经济重放结果。

### 6.3 日结、保证金与资金

- 采用成交基准的经济盈亏模型。券商逐日结算现金不进入 Rf、Rs、Co 或成本调整。
- **首版不做日结/资金对账，也不建资金对账表。** 导入器识别 Cash Report、Mark-to-Market、`Cash Settling MTM` 等段落，在预览中标为“范围外、未导入”，不作为阻断问题，也不进入经济事件。这些段落不影响经济结果；等首版稳定后，如需要再单独设计字段、来源段落、账户范围和备份格式。IB 的 `Cash Settling MTM` 定义见[官方报表说明](https://www.ibkrguides.com/reportingreference/reportguide/cashreport_comregstatement.htm)。
- 券商报表的 realized P/L 用于核对，不作为另一笔收入追加。其税务或结算基准与本账本不同时解释差异，不用 `manual_adjust` 抹平。
- 保证金占用/释放、出入金不是策略盈亏，不用作每桶成本分子或年化收益分母。首版不估算账户购买力、不复用股票资金担保口径。
- 有明确归属的融资/独立费用可记经济费用；账户级未分配费用只展示为范围外信息，不自动分摊给 CL。
- 首版没有资金对账，页面的对账状态中“现金”一项固定显示“未核对（首版不做资金对账）”，不能宣称 CL 现金已完整对账。

### 6.4 零/负价格与精度

- FUT 成交、持仓基准、市价和换月两端价格接受有限零/负数；普通 FOP 报价保持非负，正负现金由方向决定。零或负 strike 的 FOP 首版识别后阻断并说明不支持（§1.2），不能静默丢弃或取绝对值。ETF/OPT 规则保持原样。
- 所有导入、手工表单、TWS 序列化、后端校验、排序、导出、对账和展示必须一致；不能仅放开数据库后仍在入口 `abs()` 或丢弃。
- 现有代码中拒绝负价或取绝对值的位置如下（2026-09-24 核对；行号会变，以函数为准）。共用路径必须改：
  - `cost_basis_executions.py::serialize_fill` 的 `price < 0` 拒绝；
  - `ib_server.py::_serialize_portfolio_avg_cost_item` 与 `_serialize_portfolio_position_item` 的 `abs()` 和正数门槛。

  只属于 STK 页面的位置由 FOP 页面绕开，不在 STK 模块里放开负价：
  - `js/cost_basis.js::_absorbAvgCost` 的 `marketPrice > 0`；
  - `js/cost_basis_core.js::computeOptionSettlementScenario` 与 `buildExecutionImport` 的 `price < 0` 检查；
  - `cost_basis.html` 换月价格输入框的 `min="0"`。

  存储层对 FUT 种类已允许负价；对 FOP 保持 `strike <= 0` 的拒绝，与本节第一条一致。
- 原始行情的“无值/哨兵”与真实负价依据来源字段和有效性判断，不能把所有 -1 当作成交价，也不能把所有非正值丢弃。
- 计算保留输入精度，点值只乘一次，展示舍入不回写。FUT/FOP 实际张数首版为整数；换月数量分摊不得产生小数合约。费用可有小数分。
- **FOP 核心和 Python 域校验不在中间步骤舍入。** 现有 STK/FUT 核心每次累加都做 `_round(x, 6)`，单步误差最多 5e-7，照搬会让任何循环小数均价（如三笔成交均价 70.333…）超出 §14.2 的容差。新代码的累加、均价、实现损益、分摊一律用未舍入的数值；只在两处舍入：页面展示，以及 §14.2 规定的费用余数分配。不能靠放宽容差来通过测试。
- CME 已说明 CL/LO 系统支持零/负 FUT 价格与 strike；账本对 FUT 价格不能以通常为正为限制。零/负 strike 首版明确阻断，不是假定它不存在。[CME 公告 20-160](https://www.cmegroup.com/notices/clearing/2020/04/Chadv20-160.html)

## 8. 存储、版本与历史兼容

### 8.1 数据结构职责

保留 `cost_basis_books` / `cost_basis_events` 作为账本和经济事件的唯一事实来源；新增 FOP 专属关系表，全部有 book/account 约束。具体 DDL 在 P1 固定，不用无结构备注或大 JSON 替代核心经济字段。

| 逻辑表（拟名） | 主要字段/责任 |
| --- | --- |
| `cost_basis_fop_books` | bookId、引擎/语义版本、支持产品清单版本；服务端每次写入核对，缺失即拒绝（§1.1） |
| `cost_basis_fop_contracts` | 合约条款的唯一存放处：合约记录 ID、bookId、FUT/FOP 类型、broker ID、root/class/localSymbol、交易所/币种、交割月/截止时间、点值/报价乘数、交割比率及规则版本 |
| `cost_basis_fop_bindings` | FOP → FUT 关系、证据状态/来源摘要、修订及取代关系；绑定必须同账本且条款一致 |
| `cost_basis_fop_event_details` | eventId、引用的合约/交割合约记录及绑定版本、O/C/C-O、经济费用类别/源事件引用、期初基准类别与时刻、交易所交易日/正规化成交时刻/排序证据（§9.2）；不保存第二份数量、现金或合约条款，也不保存周期归属 |
| `cost_basis_fop_cycles` | 周期边界（锚定事件）、关闭状态、审计修订；持仓按经济顺序、迟到费按源成交/所属期间推导归属（§1.3/§13.2） |
| 来源引用关系 | 优先复用已有/公司行动新增的正规化来源表；扩展命名空间与复合事件两腿引用；保留报表原始 Basis、Realized P/L、费用及其单位/口径证据用于核对，不再建互不相通的去重系统 |

ROLL 分组不建表（§6.2）；首版也不建资金对账表（§6.3）。

FOP 账本不用 `shares_per_contract` 承载点值；`premiumMultiplier/futurePointValue/deliverableFuturesPerOption` 只保存在合约记录中。没有旧 FUT 数据，不需要兼容映射。

现有书表的 `default_shares_per_contract` 是 `NOT NULL DEFAULT 100`，读取又直接调用 `int()`；仅新增关系表不能解决这一点。P1/P2 必须明确迁移书表：允许该列为 NULL，新 FOP 书固定为 NULL，STK 仍要求正整数且原值不变；外来旧 FUT 书的原值保留用于原始导出。同步修改建账、目录序列化、备份身份和前端默认值，不能用 1/100/1000 占位后宣称它没有含义。新 FOP API 不接受股票乘数字段。新列约束写成 `CHECK (default_shares_per_contract IS NULL OR default_shares_per_contract > 0)` 与 `CHECK (sec_type <> 'STK' OR default_shares_per_contract IS NOT NULL)`。改列需要重建父表，步骤见 §8.2 第 7 条。

合约身份只保存一份。FOP 账本的事件通过 event_details 引用合约记录与绑定版本。公共事件表的**每一列**按下表处理，没有列出的列视为遗漏，P1 必须补齐后才能冻结。**禁止用 `future_*` 通配规则清空，因为其中的 `future_contracts` 是经济数量**：

| 公共事件字段 | 新 FOP 规则 |
| --- | --- |
| `event_id/book_id/seq/client_token/created_at_utc`、`voided_at_utc/voided_by_event_id/void_reason` | 沿用公共语义 |
| `kind` | 只接受下方种类表中的种类；`share_trade/dividend/split/option_split/futures_roll` 一律拒绝 |
| `account` | 必须等于账本账户 |
| `contracts`、`future_contracts`、`price`、`cash_amount`、`fees` | 唯一经济事实；按下方种类表逐种类校验 |
| `trade_date`、`broker_timestamp` | 服务端由 event_details 的时间事实生成的展示/筛选投影，客户端提交值不采用。有正规化成交时刻时，取 `[tws] timezone` 下的日历日与本地时刻；只有交易所交易日时，`trade_date` 取该交易日，`broker_timestamp` 为空。FOP 的排序、去重、周期归属、as-of 视图都不读这两列 |
| `tag` | 固定为空串。开平语义（O/C/C-O）、费用类别、基线类别、返佣/退款标记都是 event_details 的枚举字段，不在 `tag` 里再存一份 |
| `include_in_cost` | 见 §1.3 |
| `allow_overdraw` | 固定为 0；平仓超过可用数量一律拒绝（§5.1） |
| `derived_mismatch` | 服务端按下方现金规则计算，客户端值不采用 |
| `source`、`external_ref`、`import_batch_id` | 沿用公共语义；`external_ref` 是账户内幂等键，由来源表的主引用生成，全部来源及分配在来源表 |
| `note` | 自由文本，不参与经济计算 |
| `right/strike/expiry/con_id/local_symbol/option_sec_type/shares_per_contract` | 持久值 NULL；按合约引用生成只读展示投影 |
| `future_expiry/future_con_id/future_local_symbol`、全部 `roll_to_*`、`roll_group` | 持久值 NULL，不接受写入；月份在合约表，ROLL 不持久化 |
| `shares`、股票拆股字段 | 新 FOP 不适用；拒绝非空或非默认载荷 |

FOP 账本的事件种类白名单与字段规则（CL 的每张期权交割张数为 1）：

| 种类 | 引用的合约 | 数量 | `price` | `cash_amount` | `fees` |
| --- | --- | --- | --- | --- | --- |
| `futures_trade` | 一个 FUT | `future_contracts` 非零整数，买正卖负 | 成交价，可为零或负 | `−fees` | ≥0 |
| `option_trade` | 一个 FOP | `contracts` 非零整数，买正卖负 | 权利金单价，≥0 | `−contracts × premiumMultiplier × price − fees`；报表实际现金不同时以报表为准并标 `derived_mismatch` | ≥0 |
| `option_assignment` | FOP + 交割 FUT | `contracts` > 0（关闭空头）；`future_contracts` 方向按 §6.1，绝对值 = `contracts × deliverableFuturesPerOption` | K（>0） | `−fees` | ≥0 |
| `option_exercise` | FOP + 交割 FUT | `contracts` < 0（关闭多头）；`future_contracts` 同上 | K（>0） | `−fees` | ≥0 |
| `option_expiry` | 一个 FOP | `contracts` 为关闭方向；`future_contracts` 为空 | NULL | `−fees` | ≥0 |
| `opening_balance` | 一个 FUT 或 FOP | FUT 用 `future_contracts`，FOP 用 `contracts` | 基线参考价；未知为 NULL（§9.2） | 0 | 0 |
| `fee` | 可选引用源事件（§13.2） | 无 | NULL | 负数；返佣/退款为正，且 event_details 类别必须是返佣/退款 | 0（金额只在 `cash_amount`，同一笔费用不能两列各计一次） |
| `manual_adjust` | 无 | 无 | NULL | 有证据的金额，归入 J | 0 |

E 的合计 = `futures_trade`、`option_assignment`、`option_exercise`、`option_expiry` 的 `fees` 之和 + `fee` 事件的 `−cash_amount` 之和。**`option_trade` 的 `fees` 不计入 E**：它的佣金已经包含在该行 `cash_amount` 里，从而已在 Co 中扣过一次。例如卖出期权收权利金 1000、佣金 5、到期归零，Co = 995、E = 0，完整盈亏为 995；把期权佣金再计入 E 会错算成 990。`fees` 列在 `option_trade` 上只用于展示和费用分项，不参与 E 的求和。此口径与 §5.2 的归属表一一对应。

**复合交割的经济时刻。** 期权行与 FUT 交割行的原始时间都作为来源证据保存，但报表的登记时间不等于经济生效时间，不能任选其中一端当作生效时刻。

- 有证据确定实际生效时刻时（两行时间一致，或来源明确给出行权/指派的处理时刻），以该时刻为经济时刻。
- 两行时间不一致、又无法确定哪一个是实际生效时刻时，经济时刻记为时间范围 [较早时刻, 较晚时刻]。排序按 §9.2 的歧义组规则处理：与该范围重叠的事件一起判定是否与顺序无关，不满足就阻断并要求补充顺序证据。
- 历史 as-of 视图的查询时刻落在该范围内时，受影响的 FOP 与 FUT 合约的持仓，以及依赖它们的指标，显示为不可用并注明交割时刻未确定；不显示交割前或交割后的任一状态。范围之外的时点照常计算。
- 只有交易日的交割行按 §9.2 的交易日范围处理。

客户端写入使用合约引用，不能把读取时的身份投影原样作为写包。引用在一次提交后固定，只能按 §4.3 显式修订并保留前后版本。身份补全、更正、周期边界变更都必须进入账本 digest，防止“事件数量未变但含义已变”的旧预览继续提交。

2026-09-24 核对的 v10 尚无正规化来源引用/分配表，只有事件 `external_ref` 等字段；不能把上表“优先复用”当成已经实现。P1 重新检查当前分支，若仍缺失则新增来源与分配关系，明确账户+来源命名空间的唯一性、一行分配到多事件的数量/费用上限，以及作废后仍保留消费证据。分配数值仅为来源核对依据，不再次进入经济求和。跨报表对应关系、迟到费用的源事件引用、元数据修订记录均纳入同一备份图。

来源记录保存原始行的格式、段落、行类型（§9.7 能力清单中的键）以及原始字段名与值的原文。这样 DDL 只承载领域事实（交割月、最后交易日、交易所交易日、成交时刻、标的 FUT 等），CSV 列名到领域字段的映射是随代码发布的导入映射版本，映射变化不需要改表结构。原文只作证据，不能替代核心经济字段。

存储分流必须发生在 `_resolve_shares_per_contract` / `_validate_event_shape` 之前：STK 继续原验证器，FOP 走 `cost_basis_fop_domain.py`。不能先经过股票身份/乘数补默认逻辑，再清空字段。交易、导入、冲销、重建、恢复、周期/绑定提交全部采用同一个 FOP 时间线校验入口；不复用依赖旧月份键的 `_validate_futures_timeline`。

### 8.2 迁移策略

1. 先记录实施时实际 schema 和在途迁移，分配下一个可用版本；不能在计划中锁死 v11 或重写 v10。
2. 只在临时数据库副本演练。事务内建表/索引/约束，迁移失败全部回滚；STK 事件、seq、token、现金、作废状态和拆股组逐字段不变。
3. 两台机器均无 FUT 账本（2026-09-24 确认），不设计旧 FUT/FOP 数据的语义迁移、兼容视图或 legacy 投影。迁移时仍做检查：若某个数据库含 `sec_type='FUT'` 但没有 FOP 账本元数据的账本（例如来自别处的库），该账本只允许原始事件导出与整本删除，不计算、不写入，并明确显示原因。
4. 新引擎和所有页面都不再写 `futures_roll`，存储层对新写入的该种类一律拒绝。事件种类 CHECK 中保留该值，不为删除它重建事件表。
5. 旧客户端不能向 FOP 账本写入：服务端按 FOP 账本元数据中的引擎版本核对每次写入；状态响应返回 engine/capabilities，旧版本得到明确的升级错误。STK 经济行为不变；缺少显式类型的建账请求现在拒绝，属于 §1.1 有意变更，须同时更新所有内部调用者和对应测试。
6. 含 FUT 账本的旧 v1 备份，恢复时拒绝该账本并说明原因，不按 legacy 规则接收。
7. **书表重建必须按 SQLite 文档的顺序做，不能照搬现有事件表迁移的写法。** `cost_basis_books` 是父表，`cost_basis_events` 与 `cost_basis_snapshots` 用外键引用它；`_connect` 打开连接时已开启 `foreign_keys=ON`，迁移在这个连接上运行。2026-09-24 用临时库验证过：沿用 `_migrate_v9_to_v10` 的“改名旧表 → 建新表 → 复制 → 删旧表”，删旧表时直接报 `FOREIGN KEY constraint failed`，整个迁移回滚。可用的顺序是：
   1. 在 `BEGIN` 之前执行 `PRAGMA foreign_keys = OFF`（事务内设置无效）；
   2. `BEGIN IMMEDIATE`，建新表 `cost_basis_books_new`（带 §8.1 的新约束），按列名复制全部行，核对行数；
   3. 删除旧表，再把新表改名为 `cost_basis_books`，重建它的全部索引；
   4. 同一事务内新建 FOP 关系表；
   5. `PRAGMA foreign_key_check` 必须返回空，否则回滚；然后写 `user_version` 并提交；
   6. 无论成功与否，在 `finally` 中恢复 `PRAGMA foreign_keys = ON`。

   `cost_basis_book_resets`、`cost_basis_import_batches`、`cost_basis_reset_coverage` 以文本保存 book_id、没有外键，重建后也要核对它们引用的 book_id 全部存在。迁移测试必须在开启外键的连接上运行，并断言子表的建表语句仍引用 `cost_basis_books`。

### 8.3 原子性、备份与恢复

- 追加、冲销、导入、绑定采纳、周期边界切换均使用身份 + expectedLedgerVersion + 幂等 token；事务内验证完整受影响时间线和关系。
- 同一批次的成交/交割/绑定/来源一起提交。所有日期之前的补录必须复核之后的平仓、交割和周期边界的归零条件。
- 冲销一条成交必须处理依赖它的交割来源和周期边界锚点，不能留下引用已冲销事件的关系。ROLL 分组读时推导，冲销后自动重算，无需级联。普通冲销不释放已消费的券商引用。
- 新 JSON 备份格式增加 FOP 账本元数据/合约条款/绑定/来源/周期边界的完整载荷及摘要，使用明确格式版本；保留 STK v1 的兼容导入，不能向旧 v1 塞新字段再任其被忽略。
- FOP 新备份携带其完整关系图，恢复时在同一事务验证外键、来源分配、身份、经济投影与摘要；不能先恢复事件、随后尽力恢复绑定。含 FUT 账本的旧 v1 备份按 §8.2 拒绝该账本。
- 重建会产生新事件 ID，不能直接复制旧周期锚点/费用源引用。预览必须先按唯一来源及经济等价关系给出完整旧→新 ID 映射；不能唯一映射时拒绝保留该关系，要求在同一预览显式修订或撤销相关边界/归属后才提交。恢复到原书保留原图 ID；支持恢复到不同 bookId 时须全图重映射。任一悬空/跨书引用都使整次操作失败。
- 重建/清空/恢复前存档覆盖全部 FOP 关系与原有报表覆盖证明。
- 整本永久删除精确清理所选 book 的全部关联表，保留其他账户、类型和账本。继续沿用现有单次用户确认和服务端计划凭据。
- 保留现有分页一致 digest、文件大小/消息上限和固定 token 重试约束；大批关系不能绕过 7 MiB 文件门禁或两个后端相同的 `max_ws_message_bytes`。
- 工作区 `portfolio.db` 的 recovery set 不包含 `cost_basis.db`；不因本次共用管理代码就宣称有自动备份。FOP 验收需包含新格式备份→恢复的完整经济/证据往返。

## 9. 导入与期初完整性

### 9.1 共用证据纪律

继承现有：预览后确认、整批事务、来源幂等、同引用经济修订检查、跨格式一对一认领、Order/Trade 聚合核平、佣金/币种验证、遮罩账户确认、报表正文 Period、重建与追加分离、无成交月仍核对往返 TWS 成交、同秒顺序保留及跨页版本一致。

FOP 新增字段全部参与经济/身份冲突比较。不同 underlying FUT、pointValue、交割方式或绑定版本不能因为期权可见名称相同就被去重。

### 9.2 首次导入

- 根代码筛选需识别实际 FOP optionRoot/tradingClass/underlying 关系，不能只对 symbol 做字符串相等，也不能用子串把 MCL/其他油品误归 CL。
- 不同来源的交割月字段、最后交易日、期权到期字段分别解析；格式歧义进入问题列表。
- 同一笔成交在不同来源中的日期含义可能不同。Flex 的 `TradeDate` 可能是交易所交易日（CL 夜盘成交记为下一交易日），而 Activity Statement 的 Date/Time 与 TWS 成交给的是实际成交时刻；现有导入的列名映射把 `tradedate` 排在 `date/time` 之前。
  - FOP 账本分别保存交易所交易日与成交时刻。
  - 有可靠时区的成交时刻正规化为 UTC，同时保留原文、源时区及交易日。夜盘交易日不能覆盖实际日历日；DST 重复/不存在的本地时刻没有 offset 或其他证据时标歧义，不按浏览器时区猜。
  - 缺时刻的交易日只提供时间范围，不能伪造为午夜或收盘成交。范围不重叠可排序；范围重叠或同秒时优先使用可证明的券商顺序/来源顺序，缺证据且顺序影响均价、实现损益、交割合法性或周期边界时阻断该批提交并要求补排序依据。仅当可证明交换顺序不影响上述结果时，才以稳定来源键决胜。`seq`/导入时间不构成跨文件成交顺序证据。
  - 只有交易所交易日 D 的事件，时间范围取交易所时区中 D 前一日历日 00:00 至 D 当日 24:00，覆盖前一晚的夜盘。有 ContractDetails 交易时段证据时可以收窄；节假日前后缺证据时按更宽的范围处理。
  - “交换顺序不影响结果”用下面的充分条件判定，不满足就视为有影响。先把时间范围重叠（含同秒）的事件按重叠的连通关系归成歧义组。不同合约之间的事件互不影响。对组内涉及的每个 FUT 合约和每个 FOP 合约，设组前持仓为 q0、组内各事件的数量变化为 d_i，满足以下任一条件才算与顺序无关：
    1. 全部 d_i 同号，且 q0 = 0 或 q0 与 d_i 同号（纯加仓：加权均价、现金合计都与顺序无关）；
    2. 全部 d_i 同号且与 q0 反号，且 |Σd_i| ≤ |q0|（纯平仓且不穿越零：均价不变，每笔实现损益与顺序无关；期权按比例分摊后的每张剩余权利金也不变）。

    复合交割对它涉及的 FOP 和 FUT 分别判断；组内只要有一个合约不满足，整组视为顺序有影响。不带数量的费用事件不影响判定。
  - 组内有持仓归零时，周期边界不能落在组内部：边界只能放在整组之后，锚点取组内稳定来源键最大的事件，语义是“整组之后”。
  - 判定为与顺序无关的组，组内按稳定来源键排序。这个排序只为输出确定，不代表券商的真实顺序。
  - 新 FOP 比较器同时用于 JS、Python 和分页/历史重放；STK 继续原排序。服务端分页不能先按旧 `trade_date, broker_timestamp, seq` 裁切，再在浏览器重排。
  - 跨格式去重键和交割配对不能依赖在不同来源中含义不同的日期字段。
  - 各来源字段的实际含义在该行类型的真实格式验收中核实（§9.7）。验收前按最保守的解释处理：Flex `TradeDate` 视为交易所交易日，只提供时间范围；FUT 的 `expiry` 类字段视为最后交易日，永远不当作交割月。
- 逐合约使用 `期初量 = 期末量 − 期间净变动` 证明数量，再扣适用 cutoff 的已存持仓及已证明重复部分。
- FUT 期初必须有可解释的成交成本或明确结算基准。名义 Basis、当日结算价、broker AvgCost 与原始成交均价不能任意互换。
- FOP 期初净权利金未知时可保留数量存根并标成本不完整；不得用零权利金假装准确降本。冲突成本证据阻断。
- 记录账本范围是“自完整历史起”还是“自某基线起”。后者不能生成基线之前的 Rf/Rs，不能与完整历史账本的累计盈亏混称。
- 具有新期初语义的临时基线必须与以后报表的经济参考时刻匹配；不能用已日结重置的成本加上整段原始成交损益造成重复。

首版基线写包使用 `opening_balance`，由 FOP 域独立解释：FUT 用 `future_contracts`，FOP 用 `contracts`；现金和费用均为0，基准类型/时刻及证据在 event_details，不伪装成真实成交。缺期权成本时 `price=null`，未知与真实零价严格区分。只有绑定已确定的持仓才能进入依赖 FUT 的基线估值。

**基线的金额守恒单独定义。** “自 B 时刻起变化”只有在 B 时刻逐 FUT/FOP 的参考价格与全部期间经济事件均完整时才可展示：FUT 均价初始化为 B 的参考价、期间 Rf 从0开始，`O_B = Σ[B时刻期权有符号张数 × 报价乘数 × B时刻期权参考价]`。公式为 `Rf_B + Uf_B(t) + Co_自B后 + Vo(t) − O_B − E_自B后 + J_自B后`。`O_B` 是期初价值抵扣，不是现金收入，不混入 Co/Rs；t=B 的变化必须为0。只有原始开仓成本而没有 B 时刻参考价的记录，可用于已知数量/成本分项，不能套此期间公式。

基线前的累计实现、卖方收益或净权利金未知时，不展示延续全历史的降本价；以后全部平仓并显式开启新周期，可只对历史完整的新周期显示。补齐早期历史须经有存档的原子替换，移除相应临时基线再重放；不能让基线数量/`O_B` 与真实开仓并存。F19/F42 同时验证有价、缺价和补历史三条路径。

### 9.3 后续追加与 ROLL 来源

新报表的每条真实 FUT 行按自身来源独立核对和去重，再规划交割。换月两腿各自去重：TWS 已有其中一腿时只补另一腿，不因换月而整组阻断，也不写聚合 ROLL。ROLL 分组在读取时推导（§6.2）。

期权消失既可能平仓、到期也可能交割；FOP 与 FUT 的相关行必须由事件证据区分。只见 FUT 交割差额时，不允许先采信 FUT 而把旧 FOP 永久留在未平仓。

### 9.4 缺失、歧义与更正

对于与该账本有关但无法识别/不支持的经济行，显示明确问题，不能过滤后说“导入成功且完整”。文件归属、重复、币种、数量、交割身份冲突使该次提交整批失败。仅已唯一确认的普通交易缺绑定可按 §4.3 保存为待补全，并使覆盖状态保留限制。

绑定采纳改变逐月归属但未改经济金额时，也要重算相关持仓/覆盖/对账证明。经济更正沿用冲销或有存档的重建，不改历史行、不通过写入相反的无来源调整来修平。

### 9.5 全历史、跨报表与实现损益核对

1. 正常工作流允许按时间连续导入多份月报/年报，并补入更早历史；后台重放按经济时间与已证明的顺序进行，不以文件导入顺序代替成交顺序。报表内同秒且缺进一步证据时按§9.2判断可交换或歧义，不能回退到导入seq。
2. 旧月开仓、旧月平仓、新月开仓可能分别出现在不同文件中；已存历史提供平仓成本支持。两条换月腿跨日、跨月、跨年或分别导入，都不要求相同 timestamp 或同一 CSV。
3. 各期货月份平仓时立即结转其实现损益；月份归零后仅从“当前持仓”移出，完整成交和累计盈亏仍在账本。新合约不重置旧合约的利润/亏损。
4. 年报、月报与 TWS 成交重叠时，同一成交只参与一次数量、损益和费用；正常逐月追加、完整年度重建以及补入更早历史的最终经济状态必须一致。
5. 报表不足以支撑原开仓、期初成本或更早累计损益时，明确指出缺少的合约/时间区间。只凭当前持仓或一份近期报告不能恢复未提供的全部历史；不得称“全历史已核对”。月份缺口和期末净仓为零的历史期间仍须检查。
6. 保留报表原始已实现盈亏供核对，但不能再次收入账。核心加权平均口径与报表成本批次/费用口径可能不相同时，显示原值、计算值及可证明的口径差异；不能声称逐笔实现数字必然一致，也不能用无来源调整抹平。统一口径后的完整经济盈亏必须守恒；要求逐批次完全复刻时需取得明确的批次证据再扩展。
7. 大历史仍遵守消息/事件上限。超过单次上限时明确引导按连续期间分批，保证每批可独立校验和幂等重试；不得静默截断或把已提交前缀标为全文件导入完成。整本重建若超限，必须在替换活动历史前拒绝，不能先清空再分批写入。
8. 页面提供按期货合约、日期区间和周期的已实现盈亏明细，能追到原始开平仓和费用。ROLL 面板单列平旧实现损益、两腿价差与费用；它们的含义不同，不能相加成第二份损益。

### 9.6 连续三次换月的强制算例

同一周期持续持有 CL 多头 1 张、点值 1000，最初 A 月买入价70；各行可以位于不同月份/年度CSV：

| 换月 | 旧月平仓价 | 新月开仓价 | 本次平仓毛损益 | 累计 FUT 毛实现损益 |
| --- | --- | --- | --- | --- |
| A → B | 68 | 69 | -2000 | -2000 |
| B → C | 72 | 72.5 | +3000 | +1000 |
| C → D | 71 | 70.8 | -1500 | -500 |

另有已结算卖方期权净收益1200，未包含在该收益中的期货费用合计30，没有未平期权。必须得到：

```text
D月实际开仓均价 = 70.8
延续的等效回本价 = 70.8 − (-500 + 1200 − 30) / 1000 = 70.13
D月市价71.8时，累计经济盈亏 = -500 + 1000 + 1200 − 30 = 1670
```

全部合在一份CSV、分为跨年月报、重复导入重叠年报、没有ROLL配对证据四种路径必须给出相同结果。A/B/C月全部退出当前持仓后，历史累计 -500 仍然存在。若再以71.8平掉D月，FUT累计毛实现为500，最终策略已实现为1670，回本价变为不适用；不能因全部平仓而抹去这笔结果。

### 9.7 行类型能力清单与真实格式验收

真实报表能覆盖哪些行类型，取决于用户实际做过哪些交易。计划不能要求一次凑齐所有类型才能发布，所以真实格式验收按行类型逐项进行，与存储结构、核心计算的验收分开。

- **行类型键。** 导入器把每条 CSV 行归入一个键：`格式/段落/资产类别/事件`，例如 `activity/trades/FUT/trade`、`activity/trades/FOP/trade`、`activity/trades/FOP/assignment`、`activity/trades/FOP/exercise`、`activity/trades/FOP/expiry`、`activity/trades/FUT/delivery_leg`、`flex/trades/FUT/trade`。周度与月度期权的行格式相同时共用一个键；它们标的 FUT 的差别由 §4.3 的绑定证据保证，不靠 CSV 格式验收。
- **状态。** 每个键有一个状态：
  - `real_verified`：已用脱敏真实样本验收，记录样本编号、验收日期和导入映射版本；
  - `synthetic_only`：只有合成样本通过；
  - `out_of_scope`：可识别、按设计不导入，例如 Cash Report 与日结段落（§6.3）；
  - `unsupported`：可识别的经济行，但首版不支持，例如现金结算期权、零/负 strike（§1.2）。
- **单一来源。** 清单是随代码发布的版本化常量，放在一份 JSON 中，JS 导入器与 Python 域校验读取同一份；页面通过状态响应的 `capabilities` 获得。它不是运行时开关，改状态就是一次代码变更。
- **预览。** 所有行都解析并显示其键与状态；无法归类的经济行照旧是问题（§9.4）。
- **提交。** 服务端核对提交包中每条来源记录的键：只有 `real_verified` 的键可以写入。批次中只要有 `synthetic_only` 或 `unsupported` 的经济行，整批阻断，提示哪个键尚未验收或不支持，不能过滤后宣称导入完整。`out_of_scope` 的行不阻断也不写入。
- **例外处理。** 只适用于 `synthetic_only` 的行，即领域规则支持、只是报表格式尚未验收的记录。用户可以手工录入该事件，标为 `manual_attested`，并引用该行的来源键。认领时服务端核对手工事件与解析出的该行一致（种类、合约身份、数量、价格、费用、时间或时间范围），不一致就拒绝认领；认领后同一文件的这一行视为已覆盖，批次即可提交。手工事件在页面上始终显示为人工核实。
- **`unsupported` 的行不能认领。** 现金结算期权、零/负 strike 等首版不支持的记录，不能用手工录入认领，也不能改用其他种类或合约录入来绕过（§1.2）。含这类经济行的批次保持阻断，直到该产品按 §1.2 的门槛进入支持清单。
- **升级为 `real_verified` 的条件：**
  - 有该键的脱敏真实样本 fixture；
  - 导入结果与独立核对的期望一致，包括数量、价格、费用、现金、合约身份和时间；
  - 同一成交出现在另一格式时，跨格式去重测试通过；
  - 结果记入 `COST_BASIS_FOP_VALIDATION.md`。
- **与存储结构脱钩。** DDL 与协议不依赖本清单：来源记录保存原始字段原文（§8.1），新增键或修改映射不需要改表。真实样本如果暴露出新的**领域**事实需要存储，按正常的 schema 变更另行迁移。
- **发布。** 核心、存储、页面的验收全部通过后，P6 开放 FOP 账本的写入；CSV 导入按键逐项开放。一个 `real_verified` 键都没有时，CSV 只能预览，写入只能走手工录入。页面列出哪些行类型当前可以导入。
- **只读预览。** P4 验收后，FOP 页面可以不建账就对真实 CSV 做只读预览：解析、内存重放、显示结果与问题，不写库，也不需要写入 capability。这是真实格式验收的入口，也可用来与 IB 报表的已实现盈亏对照。

## 10. 只读 TWS 与双后端协议

### 10.1 服务边界

`cost_basis_ws.py` 继续负责账户/账本权限、消息形状和错误映射；数据库写事务仍在存储层。`ib_server.py` 注入只读 FOP 合约解析/行情函数，`historical_server.py` 提供相同协议与明确 capability/error，不假装支持 TWS。

保留 loopback、显式 trusted peers/remote opt-in 行为，不顺带更改 Origin 或部署权限。异常必须转换为对应 requestId 的失败响应，不能中断承载其他页面订单监督的共享连接。

### 10.2 新增接口职责（拟名）

| 接口 | 职责 |
| --- | --- |
| `request_cost_basis_fop_contract_details` | 有界解析账本/导入预览中的合约；返回真实条款、FOP→FUT 候选证据；不写库 |
| `request_cost_basis_fop_market_snapshot` | 对当前有效账本涉及的 FUT 与 FOP 取一次行情；返回逐合约报价与缺项；不写库 |
| `commit_cost_basis_fop_metadata` | 显式采纳绑定、设置或撤销合法的周期边界；使用 typed operation、身份/版本/token，不接受任意表/SQL |

已有 append/import/void/backup 等接口增加有版本的 FOP 数据包，保持其事务契约。所有新动作同步登记到前端出站白名单与两个后端；不提供下单、exercise 或行情订阅动作。

后端根据 bookId 读取范围，不信任浏览器另传的 account/root/currency。导入前合约查询限于已解析候选，限制单批数、并发和超时，不能变成无限期权链扫描器。

### 10.3 行情与持仓对账

- FUT 报价按真实 conId/合约月映射，FOP 报价必须对应完整期权身份与真实 underlying FUT；相同 root 不共享市价。
- 每条返回 bid/ask/last/mark、使用的价格来源、时刻、marketDataType、有效性和失败原因。预设 mid 估值；可选多头 bid/空头 ask 的平仓参考；缺侧时按下条降级并标注，不默默替换。
- 估值按固定顺序降级，每一级都在该合约旁标注，汇总处显示所用的最低一级：
  1. 批内同步且新鲜的 mid；
  2. 无可用 mid 时，使用新鲜且有效的平仓方向单边价：空头用 ask、多头用 bid，标注“单边保守估值”；FUT 同样按持仓方向处理。空头只有 bid、多头只有 ask 时不能使用该错误方向报价；
  3. 仍无适用报价时，用有日期和来源的上一结算价，缺失再用上一收盘价，标注“结算/收盘参考”及实际日期，此时完整盈亏只能显示为参考值，不显示为实时；
  4. 以上都没有才判为不可用。

  零 bid 是否有效必须结合来源有效标志/数量判断，不能用真假值判断。交叉 BBO 不取 mid，也不选其一侧冒充实时，可降级到独立有效的结算/收盘参考；身份冲突则整份合约报价不可用。已归零合约不要求报价，已实现分项不因当前缺报价消失。
- 负 FUT mark 可以有效；缺数据、过期、交叉 BBO、错误身份不可冒充有效 mark。不同月份只有部分价格时不输出完整组合当前盈亏。
- quoteBatchId + 请求 generation + ledgerVersion 共同约束展示；最多 60 秒批内时刻差作为初始同步门槛，陈旧/延迟行情明确标示，不能借用上次失败合约的报价拼一批。
- 批内同步之外还验证绝对新鲜度：实时行情初始沿用主页面 120 秒门槛，以可证明的行情/采样时刻校验，不用页面收到响应的时间重新盖新日期。延迟、冻结或收盘报价只可形成明确标示的历史参考估值，不显示为当前实时盈亏；无可靠时刻时不能声称同步。
- 同 conId 查询可去重，超时和失败不能永久缓存成成功；断线时清理本次资源，不取消其他页面共享的解析任务。
- 复用现有受限后台快照调度：合计连接级/进程级预算，不为新增端点另开无界池；写请求保持顺序，行情繁忙及时返回对应错误。
- 持仓数量始终按账户+完整合约核对。Qty matched、AvgCost matched、绑定完整、现金是不同状态，不能合成一个误导性的“已全部对账”；首版“现金”固定为未核对（§6.3）。
- AvgCost 只是旁证；单位是否已乘点值、符号、基准时刻必须验证。真实持仓快照不能恢复全历史费用与已实现收益。
- TWS 不在本机的账户仍可离线建账与导入；没有其持仓证据就不提供“采信该账户”或已对账状态。

快照是临时市场观察，行情刷新本身不改变历史账本版本。用户显式保存对账快照时，保存 ledgerVersion、quoteBatchId、逐合约报价及完整性，后续查看能还原当时的计算口径。

## 11. FOP 页面与工作流

页面保留现有产品的导航习惯，经济内容独立。

1. **总览**：完整策略盈亏/已实现结果、卖方已结算收入、买方期权结果、费用；并列显示基准范围与完整性。
2. **回本价卡**：只有 §5.3 的条件满足才显示；实际开仓均价、卖方已结算回本价、全归零假设三个标签清楚区分。没有单一价时说明原因。周期内发生过买方行权时，提示回本价受行权方式影响（§5.3）。
3. **期货月份表**：合约月、localSymbol、最后交易日、张数、实际均价、该合约 mark、对应经济浮盈亏；多空总名义暴露与净量分开。
4. **FOP 列表**：期权到期/截止时刻、C/P/K、交易类、多空张数、对应 FUT、剩余净权利金、报价、绑定状态；显示旧月期权仍在的情况。
5. **交割覆盖**：按真实 FUT 身份统计期权义务与可交付方向，不把新月 FUT 当作旧月 Short Call 的同合约覆盖。Call/Put 可能的不同结果不简单互相抵销，覆盖状态不等于券商保证金结论。
6. **ROLL 历史**：由真实成交推导（标注“有证据/候选”，不写库）；旧新合约、每腿成交、已匹配/剩余数量、两端加权价差、费用及完成状态；合计可追溯到原始事件。
7. **记账/导入/对账**：手工成交、行权/指派、到期、换月两腿录入、周期、证据补全；统一预览和现有确认流程。导入区列出行类型能力清单（§9.7），逐行标出键与状态；报表中的日结/现金段落标为“范围外、未导入”。
8. **流水/备份**：经济流水；导出含合约、绑定、原始来源和周期边界，不只输出一个成本值。导出可附带 ROLL 推导结果供阅读，恢复时不读取。

不展示“股数/每股/股息/ETF税务调整/LETF映射”等不适用控件。不沿用“成本≤0即本金全收回”的股票提示；FUT 回本价为负也不代表没有保证金需求或风险。

日期区分券商本地成交时间、交易所截止时区、用户展示时区；CL 夜盘成交的交易所交易日可能晚于日历日，两者分别显示（§9.2）。采用现有 `[tws] timezone` 与确定性事件排序；复合交割保留各来源原时间，经济时刻必须有来源或经核实的排序依据，不能为配对把两行时间改成相同。即将到期/最后交易/券商截止信息带来源；没有券商特定截止证据时显示未知，不编一个默认“强平时间”。本版只在页面展示状态，不新增后台提醒任务或自动操作。

## 12. 情景分析的交付顺序

### 12.1 首版包括可审计的交割预览

逐期权选择经核实的事件类型、数量和对应 FUT；对照前后逐合约仓位、费用、实现结果及回本价。所有生成事件只在内存中，只有用户另行确认真实记账才能持久化。

若用假设到期价格生成交割路径，必须逐 FUT 合约给价，明确“假设交割”；不能因为一个 CL 目标价就认为整条曲线同价。跨越 FUT 最后交易日的路径首版停止并要求明确处理，不自动滚仓/实物结算。实际提前指派只能来自事实事件。

### 12.2 完整压力曲线为后续独立阶段

基础记账发布不以复制股票压力测试为条件。后续 FOP 场景核心需单独完成：

- 使用 `F_month(t)` 价格曲线，可支持明确标示的平行移动、曲线斜率/跨月价差假设；默认不假设零 roll spread。
- 每张期权用自己的 FUT 价格、期限、折现和 IV；CL 美式合约按实际 exerciseStyle 选择支持的模型，不机械继承主页面的 European 默认。
- 可复用纯 American futures/Black-76 数学组件，但账本报价价值、未来期货价格变化和交割持仓路径必须独立核对。
- 零/负 FUT 或 strike 对现有对数模型不适用时明确停止该模型计算；实际事件记账、真实报价估值与到期内在价值计算不因此失效。不用 epsilon 强行塞入 Black-76。
- 盈亏按 §5.2 的经济变化计算；数量试调不能移植旧历史成本。默认只计算当前持仓，未来卖期权收入要显式假设，默认关闭。
- 截止时刻、逐腿交割顺序、快照同步、Worker 取消和输入版本完整；区间仅为情景范围，不宣称概率或保证金结果。

另写 FOP 压力计算契约并验收后才启用按钮。[现有压力契约](STRESS_KERNEL_REFACTOR.md)中的“估值不由成本反推、情景不写账”继续适用，股票现金公式不直接复用。

### 13.2 迟到费用的归属契约

第一轮核对发现“迟到费用归属旧周期”和“周期只由边界推导”有冲突；本轮固定如下，不再留给实施者自行选择：

- 迟到费用保留实际记账/经济时刻；event_details 可引用同账本、仍有效的源成交 `feeSourceEventId`。它的周期从源成交的经济顺序推导，不能由客户端填写 cycleId，也不能把费用日期倒填成原成交日。
- 一笔汇总费用对应多笔成交时，只有来源能证明唯一分摊才生成多条费用事件；分配总额必须等于来源金额，每条只计一次。不能证明时，在整本 E 中记录已确认属于该策略的费用，并列为“周期待归属”；整本合计=各周期合计+待归属项，受影响周期的净结果/回本价不得显示为完整。不是本策略的账户级费用仍按 §6.3 留在范围外。
- 无成交关联的当期独立费用，只有费用所属期间明确落在一个周期内才按该期间归属；跨周期且无分配依据时同样待归属，不默认扣入最新周期。费用归属 FUT/卖方/买方的类别另按 §5.2 校验，不能由 cycleId 推导类别。
- 源成交冲销时，同次提交必须给费用重新提供有效源引用，或显式退回待归属；否则拒绝。费用现金事实不能随源成交级联删除。
- 当前视图会重算已关闭周期；历史 as-of 视图只纳入截止时已经发生的费用，不把以后费用带回旧时点。原已保存对账快照不改写。
- P1落实载荷及黄金样例，P2落实关系/修订/digest/备份，P3/P4回放和导入，P5展示依据。F36 验证旧周期 R=100、新周期 R=200 时补旧成交费用10，当前结果为90/200、整本290；补费用之前的历史视图仍为100/200。

### 14.2 独立判断与测试文件

拟新增 `tests/cost_basis_fop_{guard,identity,core,import,import_pipeline,reconcile,page}.test.js`、`tests/cost_basis_fop_{guard,contract,store,domain,import_pipeline,ws,broker,randomized}_test.py` 及隔离浏览器流程。更新 `tests/run.js` 注册，而非只写文件不运行。测试文件名中的 contract 是契约/DDL样例验证，identity 是合约身份；P2后的实际迁移由store套件验证。

使用独立有理数参考模型扩展[随机回归](COST_BASIS_RANDOMIZED_REGRESSION.md)：生成原始交易，再独立序列化成报表；覆盖真实日期类型、多个月份、绑定证据、部分ROLL、费用、期初、冲销/重建/恢复。预期值不能调用生产核心。失败保存种子与最小反例。

最低验证链为：手算→独立模型→前端纯核心→真实导入预览载荷→临时SQLite→回读重放→隔离浏览器。数量按真实合约精确相等；金额容差与原始打印精度、费用舍入明确，不用宽容差掩盖乘数错误。

固定金标准按整数张数精确比较；测试用有理数参考值转为展示前数值，价格绝对误差≤1e-9、美元金额误差≤1e-7。大数随机用例若超出该精度预算，应暴露为精度问题或明确限制范围，不能自动扩大容差到美分级。与报表打印值核对时另按该来源最后一位小数的半单位计算舍入界限，汇总界限须能从组成项推导；不以“差不多”接受未知佣金。部分平仓费用不逐笔按分舍入，剩余精度在最后一次分配收回，并验证已结算+未结算净现金=原净现金。

基线最小向量：B时刻1张FUT参考70、1张Long Put参考0.5，随后FUT71/Put0.8，无交易费用，则B时刻PnL=0，随后自B变化=1300；缺Put基线价时总额不可用。单独Short FOP参考2→1，自B变化=1000，不能把期初负债2000当作新收权利金。顺序最小反例：已有1张FUT@70，同秒买1@80与卖1@75；买先则Rf=0/剩仓均价75，卖先则Rf=5000/剩仓均价80。虽在同一mark下完整经济盈亏可以相同，未证明顺序时仍不能声称已知Rf/均价。

真实样本按 §9.7 逐个行类型验收。首版希望逐步覆盖：CL FUT交易、月度与周度FOP开平仓、一次指派/行权、完整ROLL、部分ROLL/分笔、含日结现金的期间报表（验证这些段落被正确排除），以及增量与累计重叠。缺样本的行类型保持 `synthetic_only`、只能预览，不阻塞发布；普通FUT/FOP合成格式通过不能替代券商格式验收。脱敏后才能作为测试fixture，不提交用户真实账户资料。真实报表原件放在仓库之外或已被 gitignore 的目录；仓库是公开的，提交前对整棵树扫描账号，不只扫新增行（账号会出现在账户信息段、表头、Flex 的 `ClientAccountID` 和文件名中）。
