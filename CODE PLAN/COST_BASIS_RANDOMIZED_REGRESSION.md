# 账本随机状态机回归

这套测试用于持续发现开平仓和导入流程的组合缺陷，不把随机次数视为“所有路径已证明正确”。所有账户、合约和现金均为生成数据；SQLite 使用临时目录，不读取真实账本，不连接 TWS，不发订单。

## 独立判断依据

`tests/helpers/cost_basis_random_model.py` 不导入生产代码。生成器先产生有效的经济事件，再独立序列化为 Activity/Flex 报表。预期值由 Python `Fraction` 有理数计算；每个开仓保留独立数量/现金批次，平仓按既定平均比例消耗批次。股票和期货批次独立计算数量、成本及已实现损益。另有手算金标准验证模型本身。

JavaScript worker 调用实际回放、实际解析器和实际页面导入函数，捕获页面真正用来预览的回放结果。临时数据库读取结果再交给同一前端引擎，与独立模型比较。测试不是比较两个调用相同生产函数的“预期值”。

逐步检查现金、费用、股数、每个合约持仓、已实现/未实现权利金、卖方权利金、股票均价/已实现损益和期货已实现损益，同时禁止非有限数。按绝对金额 0.0001 的误差上限容纳生产代码的六位小数舍入；数量按合约逐一精确核对，不能靠多空抵消过关。

## 覆盖矩阵

| 层次 | 随机覆盖 | 固定边界与保护 |
| --- | --- | --- |
| OPT/FOP | Call/Put、多空、加仓、部分/全部平仓、C/O 反向开仓、行权、指派、到期 | 缺少开仓、方向不符、纯 C 超额、C/O 未越过零、conId 不符、排除/撤销事件不影响余额 |
| 股票/现金 | 买卖、穿零、拆股、股息、费用、手工现金调整 | 交割现金只计算一次；丢失交割腿、错误账号仍阻断 |
| FUT | （2026-09-26 起移到 FOP 专项，见文末“P6：FUT 移到 FOP 专项”） | 本套件只保留“股票路径不能建 FUT 账本”的守卫 |
| CSV/页面 | Activity/Flex、重叠累计报表、同秒事件、重复导入、整本重建 | 同引用经济内容修订、跨格式一对多、缺失历史与账号保护继续由原固定套件验证 |
| TWS/CSV | 用生成的 execution_report 记录模拟已有真实成交，核对 CSV 后续追加和去重 | 仅测试导入匹配，未连接真实 TWS 或测试其回包格式 |
| SQLite | 随机分批、同批重试、重复批次、乱序完整历史、重建、存档恢复、撤销末笔、JSON 恢复 | 已撤销引用不可复活；损坏备份、陈旧版本、坏批次全部拒绝；失败不改变活动记录、导入记录或重建存档 |
| 并发 | 两个写入线程同时使用同一个已审阅版本 | 必须恰好一个提交、另一个因版本变化被拒绝 |

同秒输入顺序仍是合法的顺序依据；测试只在保留原 `seq` 或具有明确可区分券商时刻时任意打乱顺序，不把无法证明的先后关系当作“已知正确”。

## 本轮发现并修复

1. **原子批次被中间状态误拒绝**：逐条插入时立即校验，可能在整批开仓尚未插入前拒绝平仓；补录的平仓/开仓对也可能暂时使已有后续平仓悬空。现在在事务内插入后校验完整受影响时间线，通过后才提交。真正缺失开仓依然使整个事务回滚。
2. **调整乘数取决于数组顺序**：缺少乘数的平仓行先到时，会错误采用默认 100。现在先读取整批明确且有效的乘数，唯一时才推导；多种乘数并存时要求显式给出，单笔与批量路径一致。
3. **正常同秒新增成交误判为修订**：种子 95 的累计报表原样保留旧成交，又新增同秒同合约的不同成交；旧记录被重复用作新成交的“疑似被修改记录”。现在原引用及经济内容均保留的旧行不再充当另一行的修订候选。现金同日新增适用同样证据规则。跨格式别名不算原引用证据，真正修订及一对多匹配保护继续有效。已缩减为两笔成交的永久回归。

这些是对 C/O 修复的后续加固，并未通过删除告警或允许不完整账本来让测试通过。

## 运行与复现

需要 Python 3 和 PATH 上的 Node，不需要额外 Python 包。

```sh
# 小型固定种子 + 最小反例，每次正常测试都会运行
python3 -m unittest discover -s tests -p cost_basis_randomized_test.py

# 较大批次：首 500 个种子同时走真实临时数据库
python3 scripts/verify_cost_basis_randomized.py --cases 3000 --steps 80 --store-cases 500 --report ledger-random-report.json

# 复现曾暴露同秒累计导入问题的历史
python3 scripts/verify_cost_basis_randomized.py --seed 95 --cases 1 --steps 80 --store-cases 1
```

失败立即退出非零状态，输出种子、阶段和精确重跑命令，在系统临时目录保存生成输入。可用的纯回放/完整 CSV 反例会进行最多 120 次删减尝试，只保留合法的经济历史；复杂重叠导入/事务序列失败保留完整种子，不伪造一个不同原因的“最小反例”。缩减器也有故障注入单测。

GitHub Actions 对相关 PR 自动运行固定回归与 300 个随机种子（60 个含数据库），上传覆盖统计及失败输入；也提供手动运行入口，没有添加定时任务。

## 拆股组随机回归（2026-09-24）

`tests/helpers/cost_basis_split_model.py` 独立生成含标准拆股的历史，并用整数分和分数预测结果，不引用生产代码。每段历史包括：

- 股票买卖与多空看涨看跌期权，含半分进位行权价（99.97、105.05、106.49）；
- 拆股前部分平仓，以及已到期但记或不记到期的系列；
- 2025-11-20 的 2:1 或 3:1 拆股，其中约十分之一只有股票；
- 拆股后在新合约上平仓、指派和到期；
- 四成历史在 2026-01-05 再做一次 2:1 或 3:1 拆股；会让两个系列落到同一新合约的比例会被跳过。

`tests/cost_basis_split_campaign_test.py` 对每个种子检查：

1. 前端核心回放的股数、现金、已实现与未实现权利金和每个未平系列，与模型一致；
2. 核心 `planSplitGroup` 根据拆股前历史生成的转换，与模型独立推导的完全相同；
3. 数据库种子逐行写入临时 SQLite：
   - 每个拆股组先提交三种写坏的版本（少一腿、只转一半、行权价差一分），必须被拒绝且账本版本不变；
   - 再写入正确版本，立刻整组冲销后重新记录；
   - 最后回放与模型比对，并做一次备份往返。

```sh
# 固定种子 0–99，其中 20 个走数据库；常规测试都会运行
python3 -m unittest discover -s tests -p 'cost_basis_split*_test.py'

# 验收规模：500 个种子，100 个走数据库
PYTHONPATH=. python3 tests/cost_basis_split_campaign_test.py --seeds 500 --start 1000 --store-every 5
```

GitHub Actions 的随机回归工作流运行固定种子；另外每次按运行编号取 500 个新种子（起点 100000 + 运行编号 × 500）。失败时输出种子、阶段和复现命令。

2026-09-24 验收：种子 1000–1499 全部通过。其中 100 个走数据库，680 次核对生成的转换与模型一致，350 个写坏的拆股组全部被拒绝，139 次冲销后重新记录，100 次备份往返。计划要求的 24 个分支全部覆盖。

另做故障注入，每项都会让这套回归失败：

- 核心不转移未实现权利金；
- 用浮点加 `toFixed` 推导新行权价；
- 后端跳过"不许漏转系列"的检查；
- 转入一侧不进入新的拆股代次。

### 身份与拆股代次（2026-09-24）

模型回归中每个系列只有一个合约，覆盖不到"同一执行价在拆股前后是两张合约"。`IdentityCampaign`（同一文件）不做模型，只检查一条性质：**后端接受的每次写入，前端核心回放都没有阻断提示**；被拒的写入不改变账本版本。每个种子：

- 拆股前：标准 K50（5001）、调整类 `2TQQQ` K50（5009，拆股前必定平掉）、标准 K100（1001），各自可能不存在、已平或持有到拆股；
- 拆股后：K100 转为 K50，合约编号沿用 1001 或换成 2001；K50 转为 K25；
- 每行随机带完整身份、只带代码或什么都不带（手工录入）；
- 拆股组按时记录，或在拆股后的行之后补记。按时记录时，页面草稿没有问题就必须被接受；
- 随机整组冲销；
- 最后用 TWS 批量归账平掉每个未平系列：页面必须接受，后端必须按页面给出的证明写入。

```sh
# 常规测试运行 80 个身份种子；命令行默认 200 个，可单独运行
PYTHONPATH=. python3 tests/cost_basis_split_campaign_test.py --seeds 0 --identity-seeds 1000 --start 7000
```

2026-09-24：种子 0–499 与 7000–7999 通过，11 个必测分支全部覆盖。旧代码上它发现了验收后审查的三个问题和一个新问题（后端 TWS 证明不分代次），详见拆股计划 §15.12。

## 边界

- 不是对无限输入空间的证明；生成器不可能代表所有 IBKR 本地化格式、修订样式、网络中断顺序或未来公司行动。
- 本套件只生成 STK/OPT 历史。FUT 与 FOP 的随机回归在 FOP 专项（`scripts/verify_cost_basis_fop_randomized.py`，见文末）。
- 已有异步换账本、导入模式切换、遮罩账户、真实报表、协议校验等固定套件继续保留，随机测试没有替代它们。
- 权利金使用本产品既定的比例分摊，未验证 IBKR 的逐税务批次损益；本轮不修改定价/压力测试内核。
- 真实报表测试只在本机按显式文件路径执行；不把用户账单上传到 GitHub。

## P6：FUT 移到 FOP 专项（2026-09-26）

股票页面、核心、导入器和存储里的旧 FUT/FOP/ROLL 分支在 FOP 独立账本的 P6 阶段退役（`CODE PLAN/COST_BASIS_FOP_STANDALONE_PLAN.md` §13.3 P6）。本套件原来在奇数种子上用旧引擎回放 FUT 历史，现在所有种子都是股票历史；奇数种子仍检查“股票路径不能建 FUT 账本”。

- **股票套件（退役后）**：`--seed 0 --cases 3000 --steps 80 --store-cases 500` 全部通过，用时约 492 秒。核心逐步检查 250,568 次，Activity/Flex 页面场景各 12,000 次，数据库状态机 500 个，并发版本争抢 50 次，FUT 建账拒绝 250 次。
- **FOP 专项**：`scripts/verify_cost_basis_fop_randomized.py --seed 0 --cases 2000 --steps 80 --store-cases 300`。生成器产生原始成交（期货、期权、分笔订单、部分换月、提前指派与行权、到期、佣金、负期货价），测试专用写报表脚本写成 Activity（中/英）或 Flex，真实导入器预览、临时库分批导入、重复导入、撤销末笔、迟到费与调整、备份恢复到另一账本，每一步与独立有理数模型比较。失败时输出种子、阶段、原始动作，并缩减到同一阶段仍失败的最小动作列表，可用 `--replay` 重放。2000 个种子（200,144 个事件，其中指派与行权 20,558 个、负期货价 4,364 个）全部通过，用时约 85 秒。
- FOP 专项在首次运行时发现两个真实问题，都已修正并补了固定测试：后一份 Flex 报表只用 conId 写明期权的标的期货时，导入器找不到账本里已有的期货；已存为待补全的绑定，后来的报表证明了它也无法补齐，导致交割被阻断。详见 FOP 验证记录的 P6 部分。
